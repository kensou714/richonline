# 洗牌卡1125的Lua规则与核心库存事务

日期：2026-10-11。仅代码、静态核对及编译；未新增/执行测试、未启动游戏或服务。

## 迁移范围

- 请求152仍为6字节：操作号、日历、零基槽位、主背包0。`card.prepare`复核当前掷骰阶段、角色行动权、日历与卡归属；准备扣除一张1125。
- Lua读取扣卡后的非空卡叠，对其做Fisher–Yates排列。保持原有模拟器“只洗已有卡叠、不生成新卡”的策略，不声称恢复官方随机算法。
- 40E8结构为：2字节操作号、2字节游戏号、槽位、背包0、卡叠数、保留0；随后每叠为2字节卡号、1字节数量、1字节角色。本轮沿用已有 `prepare_shuffle` 协议，没有新增客户端反编译取证。
- `prepare_shuffle_order`由原生兼容和Lua核心接口共享。必须恰好覆盖所有扣卡后非空原槽；通过真实资源 `add` 按回包顺序重建手牌，包括CombCard合成。不能直接对服务端数组换位，否则可能与客户端逐条插入后的结果不同。

## 静态核对

- 最后一张洗牌卡用完后，Lua传 `core.array()` 空顺序，生成8字节空手牌确认；核心接受全部槽位确实为空的情况。
- 洗牌卡叠仍有余量时，其余量作为普通卡叠参与排列；总扣卡次数仍为一次。
- 重复、空槽、越界和遗漏均在准备器拒绝；卡叠数量必须为1..127且卡号存在于资源。
- 核心在Lua完整返回后核对唯一40E8与准备结果逐字节相同，拒绝混用资金、位置、状态、地面、地产、关系、移动或清除计划，并检查待提交库存未被后续接口改变。
- 准备/脚本失败沿用400B恢复；最终提交前复核原库存。日志增加 `inventory_reorder`。网络失败不等于内存事务回滚，沿用既有连接处理。
- `server/scripts`也是安装版脚本目录，因此脚本检测新核心能力；旧EXE不具备该能力时，在任何准备调用前进入原生兼容入口。未替换当前测试EXE、客户端或数据库。
