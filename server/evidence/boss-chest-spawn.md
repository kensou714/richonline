# 战后宝箱的连通候选与 Lua 选点

## 代码审计发现

`Turns::open_chest` 原先把所有有邻格的道路加入候选。该条件只能排除单个孤立格，不能排除与玩家所在道路不连通的一整片区域，和已有文档描述的“连通道路格”不符。本轮是静态审计发现，没有新增实机故障日志，也不把它作为此前胜负双提示或回 1 血的原因。

## 实现边界

核心从玩家当前格遍历道路邻接关系，并沿 `RichonlineRoadTopology::portal_destination` 加入原资源定义的成对传送边。候选仍按地图位置升序排列，排除玩家脚下和无邻格的位置。完全连通的地图保留原候选顺序及一次随机调用；不承诺三回合内一定有合适骰点抵达宝箱。

`bosses.chest.spawn` 通过新增的 `boss.chest_spawn` 事件选择位置。C++ 提供只允许读取一次、绑定候选数量的随机结果，并逐值复核 Lua 返回的位置。Lua 不能增加候选、重抽位置或提交地面对象。脚本异常、错误类型或篡改结果均发生在地面、手牌和状态清理计划提交之前；BOSS 胜利在进入此函数前已由原结算事务持久化，不声称脚本错误会回滚既有胜利。

选点后继续使用现有 `420C`、NPC32、`0002` 开始奖励回合，以及拾取或第三次完成回合才释放结算的流程。奖品仍由独立的原资源权重抽选及幂等库存事务处理。未配置脚本的底层调用者也使用相同的连通候选。

本轮只编译 C++ Release 并检查 Lua 语法，不新增或运行测试，不启动本机服务和游戏。实机拾取、提示与三回合行为仍需要玩家验证。
