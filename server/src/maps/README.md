# NEW map packages

This directory contains immutable per-map descriptors. The registry matches both the wire map name and category; it never falls back between ordinary and special resources when the map identifier is the same numeric value (map index 11 occurs in both `BS_1_1.emp` and `V_BS_1_1.emp`).

The catalog covers all 13 shipped BossWar scenarios: Black Beibei `BS_1_1` through `BS_1_4`, A Zhan Bo `BS_2_1` through `BS_2_4`, Kid Ken `BS_3_1` through `BS_3_4`, and Zhao Ling'er `V_BS_1_1`. Each group has its own source directory and each scenario has an independent descriptor. `richonline_map_packages()` enumerates these descriptors without fabricating readiness. E88 category 2 selects special resources; every other DWORD selects ordinary resources. The known HTTP LobbyType names emit 0–3, but the BOSS consumer does not impose that enumeration as a wire bound. Preserve the original category bits and still reject every cross-table map-name mismatch.

Each package owns resource loading and any implemented chance-card policy. `RichonlineBossStage` remains the shared bounded resource parser: it selects an exact `mapName` record, reads its `mapIndx`, then verifies the EMP metadata rather than deriving identifiers from file names. Socket framing, SQLite, lobby state and game-turn orchestration remain outside this layer.

`RichonlineMapReadiness::partial` is intentional. Zhao Ling'er has independently parsed `V_BS_1_1.emp`/`BossWar_v.kpd` resources and a static card event candidate (event 2, card 1038), but complete gameplay/BOSS hook closure is not enabled. Registering the package makes resource inspection and future wiring explicit; it does not claim that the map is playable.

`runtime_enabled` separately permits the known partial runtime for Black Beibei 1-1 and disables all other scenarios until their remaining events are closed. It must not be interpreted as complete gameplay readiness. Resource loading and package tests work for all 13 packages regardless of this runtime gate.

The legacy policy's opaque bytes are copied without interpretation. Black Beibei binds its own map while preserving configured event/card fields for existing deployments; their downstream resource validation still applies. Zhao Ling'er binds event 2 and card 1038 explicitly, regardless of a legacy map's event/card values. Card 1038 is a temporary implemented reward policy, not the complete official event distribution. Unknown events, BOSS behavior and card catalogs remain unsupported until IDA/runtime evidence is added.

Newly cataloged scenarios have absent `chance_event`/`reward_card` options. Their `configure` operation reports `richonline_map_chance_policy_unimplemented`; it does not inherit card 1038 or an event belonging to another map. The `V_BS_1_2` preview has neither an EMP nor a BossWar_v scenario row in the installed NEW client and reports an explicit missing-resource error. It is not registered as a playable scenario or identified as Li Xiaoyao.

Evidence: `protocol-analysis/richonline-rebuild/game/startup-flow/map-unlock/character-boss-catalog.md` records decoded BossWar entries, hashes and absence of the orphan preview's resources. `boss-entry.md` records NEW category selection (`627F40 → 7B2850/7B29B0`) and the HTTP category names. `coverage/resources-boundaries.json` independently inventories all EMP headers. Tests use actual NEW resources, verify all boss identities and exercise map-index mismatch and parser size limits; they do not claim client gameplay validation.

`coverage/map-category.md` and `map-category.raw.json` record the fresh BOSS create-validation audit: `7F2790` accepts mode 3 before its non-BOSS category switch, so a category upper bound of 3 was removed. This does not widen the HTTP parser's string enum or imply that an unknown category should be advertised as a channel.

Future map-specific event and BOSS hooks belong beside each map descriptor and should use shared typed gameplay operations. The package is the sole map-selection boundary: shared gameplay resolves it once from the validated wire map name and category, then consumes its typed fields. Do not add a `map_name` conditional to a shared turn, landing, card, NPC, or combat handler. A newly proven per-map behavior must add a typed package configuration field with its definition in that map's source directory, plus parser/runtime evidence and a focused test. No inheritance hierarchy or general plugin loader is required. Registry entries remain immutable; transport and account storage do not move into a map package.

`closed_chance` now owns each map's implemented landing-event policy: playable reward-card IDs and whether motion statuses are enabled. Only Black Beibei 1-1 explicitly selects cards 1038–1041 and motion effects. All unopened maps, including Zhao, leave this option absent. The session must require this configuration before calling the shared closed-event builder; it must not insert fallback IDs. This policy describes current server capabilities, not recovered historical probabilities. Event-table reading, safe candidate filtering, packet encoding and ledger commits remain in shared gameplay.

`raw_status_policy` explicitly opts a package into the audited raw client-status
model. Only BS_1_1 currently selects `closed_boss_initial_status`: its reachable
mode3 effects never enter hotel/hospital/jail/kidnap or scripted NPC32 states.
The runtime may then bind timed-bomb and hibernate callbacks to its per-room
raw authority. New maps must audit those transitions before opting in; they
must not inherit BS_1_1 constructor assumptions merely by using shared combat.
If a new effect can write these fields, implement its verified authority
transition or invalidate the field before exposing the effect.

`closed_npcs` similarly contains configuration only: Black Beibei 1-1 selects NPC kinds 0, 1, 2 and 3; starts with four gods and one ticket chest; maintains two to five objects; refreshes one after every three completed rounds with chest refresh enabled; fortune rewards use cards 1038/1039; money transfer has an explicit server cap of 1000. Ticket amount is loaded from the actual GValue ITEM14 by shared NPC rules, rather than configured here. NPC2 has an explicit server policy selecting at most four inventory units uniformly without replacement; stacked cards may supply repeated slot indices only while enough units remain. This is not a recovered original probability law. Other maps leave the policy absent. Runtime callbacks, actual actor team values and opaque spawn wire bytes are supplied by the session's proven profile/bootstrap policy, never invented here as zero defaults. Updated configuration alone does not certify live UI verification or all other god effects.

`combat` and `opening_hand` also hold pure scenario configuration, currently BS_1_1 only. The combat descriptor selects four 80/10/10 trials and an explicitly uniform missile/nuclear/safe-nuclear variant list, visible targets including self, action-status checks and no hand consumption. Opening inventory requests one 1038 and one 1044 for the human and no BOSS cards. These fields do not activate runtime behavior by themselves; the shared session binds their proven protocol/state adapters exactly once. NEW4019's 30-byte/four-record receiver and constructor tails have been independently established in `game/startup-flow/opening-hand/findings.md`. See `coverage/map-scenario-runtime-audit.md` for resource differences and participant limits.

Every descriptor also owns an independent `resource_rules.expected_static_types` boundary. `rule_resources.cpp` applies the shared NEW phase1 classifier and actual phase2 property references, validates that exact map's static set, retains the complete EMP tail arrays and prebuilt state, and parses portal28/61 pairs and source NPC records without copying another map's runtime policy. The pure `richonline_map_rule_resources(stage,emp,specification,price_base)` is available for bounded parser verification. `load_richonline_map_rule_resources` supplies exact package resources. All13 installed tails are consumed exactly; absent source NPCs are not replaced by invented spawn data.

The shared spawn selector uses an explicit per-package policy. Twelve maps retain `all_candidates_connected`; BS_2_2 selects its largest adjacent-road component, with a deterministic lowest-position tie break, then applies the same first-straight/farthest-candidate rule within that component. On the installed NEW resource this yields83/1 and233/1. The old conservative selector remains available and still rejects BS_2_2 as disconnected; no graph edge is fabricated. Source arrays whose downstream meaning is not established are retained exactly, including repeated values. `coverage/map-closed-capabilities.md` and `.json` distinguish source availability, reachable client phases and remaining runtime closure for each map. The additional12 runtime gates remain false.

`legacy_richonline_map_package()` returns the Black Beibei descriptor only for parsing the existing global `richonline_boss_card_policy` schema. A game session must select by its actual map name/category and call that package's `configure`; this helper is not a runtime fallback for unknown maps. Shared session wiring belongs in `src/gameplay/boss_session.cpp`.

## Adding a scenario

Create or extend the descriptor in the owning boss directory, give it the exact wire EMP name and category check, and keep resource-specific validation in `resource_rules`. Populate an optional policy only when its wire fields and game effect have been verified. An absent option means the shared runtime must reject or gate that feature explicitly; it must not borrow another BOSS's values. Add the descriptor to the registry factory, verify it against the installed EMP/BossWar resources, and keep `runtime_enabled` false until its complete supported turn path is wired. This makes Black Beibei, A Zhan Bo, Kid Ken, Zhao Ling'er, and future BOSS maps independently maintainable while preserving one shared protocol and state-machine layer.
