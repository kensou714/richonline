// 先确认目标
// 每项工作写明目标客户端 SHA256、资源指纹、地图/模式和用户操作。
// 纯服务通信工作另记方向、操作码和等待状态；纯内容工作另记资源依赖。
// 使用当前目录 RnClient.exe；旧客户端仅可用于差异研究，并显式标为已弃用。
// 不把旧地址、旧包长和旧字段名直接套用到新版。

// 一项事实的最小记录
// 结论：说明哪个行为已确认，避免只写“应该如此”。
// 范围：版本、资源路径；涉及通信再记方向、操作码、适用地图与状态。
// 来源：工程相对路径、函数名、IDA 地址；必要时附脱敏日志行号。
// 验证：静态证据、资源解析、编辑器往返、回归测试或真实客户端操作，分别列出。
// 缺口：未确认字段和不支持分支保留原名，不用猜测补齐。

// 状态用词
// 已核实：指向可复查证据；还要注明核实的是静态布局还是运行行为。
// 已实现：当前源码存在处理，不代表已部署或已被真实客户端接受。
// 已回归：写测试名称与构建快照；只覆盖测试明确执行的场景。
// 已实测：写实际客户端操作、观察结果和对应实例日志。
// 兼容策略：为本地运行作出的明确选择，不冒充原服务器规则。
// 待验证：记录还缺哪项证据；不要用“全部兼容”掩盖未知部分。

// 同时开发
// 开始前说明本次负责的模块、源码文件与测试，检查是否有人同时编辑。
// 共享目录内避免覆盖整个文件；修改前重新读取相关代码。
// 使用自己的构建目录，避免共用 Ninja、CMakeCache 或正在发布的 exe。
// 不为整理文档搬动运行数据、客户端资源或他人正在使用的源码。
// 资源编辑在副本中完成；保留原文件哈希、编码、顺序和可恢复备份。
// 切换服务实例前与实测者协调，保留构建记录与数据库备份。

// 注释写什么
// 解释协议约束、状态前提、所有权、单位、并发边界和异常处理原因。
// 描述“为何必须如此”，不逐行翻译显然的赋值和循环。
// 未知字节写“含义未确认”；实际不消费的字段不能宣称业务语义已恢复。
// 注释中的协议依据使用稳定函数名或地址，避免依赖容易漂移的代码行号。
// 不改错误码、日志事件名、配置键和线上标识来实现中文化。

// 文档写法
// 正式新增说明文件使用 .txt，统一 UTF-8。
// 首部用短块注释说明主题、范围与核对日期，分节用 // 中文短标题。
// 段落控制在三至五行；复杂主题拆文件，不在一个文件堆满所有材料。
// 字段清单用短定宽列；不要使用 Markdown 标题、表格、列表或代码围栏。
// 资源手册要写格式、消费者、引用键、可编辑范围和回归方法。
// 逆向资料要说明选题价值：复用范围、证据强度、内容收益和验证成本。
// 示例只给可核对的操作；路径含空格时加引号，占位符必须说明如何替换。
// 生成文件、第三方库和二进制资源不为了注释统一而批量重写。

// 交付检查
// 文档引用的文件存在，函数与字段名称能在匹配版本找到。
// 新增分支有失败场景或已有契约回归；不通过删除测试获得通过结果。
// 只改注释时比较注释之外的内容；并发代码变动独立核对，不能算作注释修改。
// 测试结果与真实客户端验收分开记录；未执行的步骤不写成已通过。
// 日志和文档不放账号密码、校验材料、完整令牌或个人数据。

// 提交或交接时
// 说明原来的具体卡点、改变后的行为、相关证据和验证范围。
// 记录构建产物摘要、配置入口与是否实际部署。
// 对仍未实现的关联分支给出明确入口，不把它们隐藏在“修复完成”中。
