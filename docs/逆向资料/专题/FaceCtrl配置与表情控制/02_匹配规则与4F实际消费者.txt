// FaceCtrl 匹配规则与 4F 实际消费者
// ============================================================================
// 一、控制词匹配
// ----------------------------------------------------------------------------
// 64D180 输入为调用方标识和文本指针。64D1A6 先 strlen，64D1B1 才判断指针非零。
// 因而 NULL 文本会先进入 strlen，后置判断不是空指针保护；空串则跳过规则扫描。
// 两层有符号循环：按记录顺序，再按记录 +4 的控制词数量；没有容量钳制。
// 64D22C 经 6103F5 到 9233F0 使用 strstr 查找记录 +8+j*8 的控制词。
// 64D243 比较命中字节偏移，64D246 jge 跳过等于或大于当前最佳偏移的结果。
// 规则：文本里位置最早的子串获胜；同位置保持最早 ITEM / 最早 ctrl。
// 不执行大小写折叠、词边界判断或最长词优先；本文不推导多字节字符边界。
// 例如 abc 与 ab 均从偏移零命中时，结果由文件枚举顺序决定，不由长度决定。
// 空别名会匹配偏移零；face=-1 命中也更新最佳偏移，但最终被 -1 哨兵抑制分发。
// 因此 face=-1 不是遍历中直接忽略的规则，还可能阻挡后续同位置的有效 face。
// 当前原包 face1..9、45 个非空别名；没有空别名和 -1 的运行触发证据。
// 不修改输入文本；返回值依分支而异，不能包装成布尔成功 API。
// 聊天 64A9F0 的 64B569、64B766 两处调用使用消息 +8 标识及消息文本位置。
// 局部调用现场没有使用返回 EAX 决定后续路径；聊天函数其他分支未在本批审阅。
//
// 二、分发参数是更新合同
// ----------------------------------------------------------------------------
// 64D272 在局部参数 +0 写 10h，64D27C 的 +4 写调用方标识，64D282 的 +8 写 face。
// 64D289 压入界面槽号 4F，64D292 经 605B76 到 6E4640 提交参数指针。
// 10h 的真实含义由 73B694 and edx,10h 确认为表情更新位；它不是消息长度。
// +0 是位掩码；+4 是与界面角色数据首 DWORD 比较的标识；+8 是 face 编号。
// 相邻 +12 没有业务赋值；局部入口调试堆栈填充 CCCC 不构成稳定的参数值。
// 本表情分支只读取 +0、+4、+8，没有读取 +12；不声明这是一份四 DWORD 网络包。
//
// 三、4F 从注册到实际虚调用
// ----------------------------------------------------------------------------
// 管理器 6279C0 保存全局 A766C8，申请 6C0 字节并调用 6E2A70；此处只复用局部。
// 6E6080：创建表始于管理器 +48h，4F 对应 +184h，值 601B6B -> 6E8F50。
// 销毁表始于 +2C8h，4F 对应 +404h，值 6084A7 -> 6ECD70；销毁目标未展开。
// 6E3B40 可以通过注册创建函数生成实例，写入 [manager+44h]+4F*84h+4。
// 6E4640 自身只取得这个已存在实例，经虚表 +10h 调用；实例缺失则跳过。
// 因而识别了控制词也不保证必定显示，创建成功与界面状态仍是外部前提。
// 6E8F50 工厂申请 93Ch 字节，经 608745 调 6FC000；只复用旧主范围字节。
// 6FC035 明确把 A27120 写入对象首 DWORD；实际虚表 +10h 为 60A72F。
// A27120 前 24 字节及 60A72F 的 E9 与当前磁盘一致，60A72F -> 73A590。
// 不靠相邻地址或自动类型名认定实际消费者，也不把候选数据窗口当作虚表证据。
// 6FC000 还构造对象 +68h 起、步长 21Ch、数量 4 的数组，保存完整异常尾块。
//
// 四、73A590 的表情位分支
// ----------------------------------------------------------------------------
// 入口 73A5D6 取得参数，保存首 DWORD 为更新位掩码；入口状态检测可能跳过处理。
// 73B694 筛选 10h 位；73B69D 至 73B6B6 遍历控件编号 100、200、300、400。
// 73B6C8 经 610297 -> 8E2C10 取得控件；73B6D9 经 60A2FC -> 6FA210 检查状态。
// 73B6ED 经 60EACD -> 8E1570 取得索引零关联数据；NULL 或首 DWORD 不同则继续。
// 73B70C 比较关联数据首 DWORD 与参数 +4，匹配才读取参数 +8 的 face。
// 73B72F 计算 this+68h+21Ch*(控件编号/100-1)，73B733 经 601EEA 调 797800。
// 797800 接受 face；现有自动库名与 COleDateTime 类型没有作为业务类型证据。
// 73B73A 取 GetTickCount，73B757 写 this+54h+4*(控件编号/100)，然后退出遍历。
// 可确认首个符合标识的活动槽收到 face，并记录提交时刻；显示时长不能由此推出。
// 本批只审阅该位分支、入口与下游边界，不把 73A590 其他更新位全部标记为已理解。
// 797800 的内部字段、图像帧资源、刷新/到期消费者，以及控件状态的具体语义仍待核。
// 故文档使用“标识”和“状态检查”而没有把未知库名转写为确定玩家类或可见性合同。
//
// 五、扩展影响
// ----------------------------------------------------------------------------
// 加别名不会自动增加 face 资源；face 如何映射到图像帧，需要沿 797800 和刷新链分析。
// 改别名顺序会改变相同位置的胜者；改文本编码会改变 strstr 的字节匹配结果。
// 编写配置工具时应提供冲突预览，直接显示原始字节偏移和最终选中的 ITEM / ctrl。
// 服务器与客户端文本流的编码合同应单独证明；本地候选解码不足以定义通信编码。
