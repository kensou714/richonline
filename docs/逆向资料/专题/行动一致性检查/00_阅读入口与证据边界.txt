// ============================================================================
// 行动一致性检查 | 当前格位与 0x4044 的队列时序
// ============================================================================
// 研究对象：当前 Richonline/RnClient.exe；不适用于上级目录的旧客户端。
// 研究用途：解释“收到事件却未继续”的本地等待，排查格位、路线与消息顺序是否一致。
// 本专题为只读静态分析；没有修改 EXE、IDA 数据库或正在运行的游戏。
//
// 首先记住的事实
// ----------------------------------------------------------------------------
// 0x4044 的处理函数是 0x662B20，直接读取一条 6 字节业务记录。
// GmsvID 不一致：显示 Error GmsvID，随后退出处理，不在该分支重插原记录。
// GmsvID 一致且目标格等于当前参与者格位：退出处理，不再重插。
// GmsvID 一致但格位不同：把原 6 字节记录插到游戏队列的当前 head 之前。
// 该处理函数没有直接发送网络包，也没有直接修改参与者当前位置。
// 因此“卡在 4044”首先是本地状态与队列顺序问题，不能单凭它判定缺少某个上行响应。
//
// 阅读次序
// ----------------------------------------------------------------------------
// 01_4044字段与重插流程.txt：业务记录、GmsvID、参与者选择、注册链、栈缓冲区。
// 02_队列消费与停滞排查.txt：head 插入的含义、先 pop 后调用、合理观测字段。
// 03_位置写入链与候选边界.txt：setter、移动 tick、5B8h 候选与误判边界。
// 函数审阅清单.json：18 个本地保存函数的语义、证据文件与未闭合项。
// 验证专题.py：仅从磁盘读取当前 EXE 并重新核对证据字节，不启动游戏、不写二进制。
// export_followups.py：在已经连接的 IDA-MCP 数据库中只读生成补充证据。
//
// 对象符号与地址口径
// ----------------------------------------------------------------------------
// G：游戏控制对象；参与者指针表 G+0xE00，当前参与槽 G+0xE28。
// R：参与者对象；当前逻辑格位 DWORD 位于 R+0x5B8（十进制 1464）。
// Q：内嵌游戏队列，Q=G+0x640；本专题的 head 指 Q+0x0C。
// 地址统一为当前 32 位 PE 的 VA；WORD/DWORD 是访问宽度，不由伪代码变量名推断。
//
// 基线与结论强度
// ----------------------------------------------------------------------------
// 磁盘 SHA256：a23410e79637e312c932f861176d8d81cd1fd5d222a286f279feccdece6263c2。
// IDA 原输入 SHA256：cb35f69f3d49c2093897d4ea2cb547a1e38b213f3a8df0af52b859f9e661de77。
// 两者整体不同；本专题函数、直接 E9 跳板、RTC/注册写入和候选指令已逐范围映射磁盘。
// 分派表槽没有对应磁盘原始节字节，IDA 当前读值仅单独记录，未当作启动初值。
// “范围字节一致”不表示整个数据库与磁盘 EXE 完全相同。
// 已证实：字段访问、条件分支、head 插入、位置 setter 与 56 条字面候选的对应字节。
// 静态推论：若格位持续不匹配，4044 可能反复占据 head，延迟后继记录的消费。
// 未证实：某次玩家现场卡死、必然死循环、4044 的正式官方名称与服务端完整调度策略。
// 本专题不将反编译的 MFC 名称当作业务语义，也不把 288 字节内部槽当作网络包长。
