/*

 * 原始类型线索来自0x82D750断言及errorscheduler.h路径；字段名按使用恢复。
 * “调度器项移除”“界面状态清除”“TCP关闭”是不同动作。
 */

// 全局调度器
//
// 0x82CCD0返回0xACB878；首次使用调用0x82CD90构造并注册析构。
// 调度器前部为按int32键查找的关联容器。
// +0C 指向尚未绑定请求键的ErrorBundle；断言名称m_pebWatingActived。
// +10 指向回调所有者的请求键清理链表；0x82D7D0设置，0x868F10读取。
// 第四批已闭合其析构用途，见05；链表非空不等于界面仍等待。
// 这两个字段是内存指针，不是网络请求序号或超时值。

// 请求登记闭环
//
// 以登录0x855790为例：分配16字节ErrorBundle(0x82D610)，
// 构造默认错误回调对象，0x82D670(default=1)设为bundle+12。
// 0x82D750把bundle暂存到全局调度器+12；已有暂存会触发assert。
// 0x82D7D0设置所有者清理链表，随后调用真正请求入口0x87DFE0。
//
// 0x868E50(key)先调用0x82CE00删除旧key及它的bundle，
// 若调度器+12非空，则插入{key,bundle}并将+12清零。
// key是32位有符号整数，实际传参和关联容器比较均不按BYTE截断。
// 如果此时没有暂存bundle，函数只清旧key，不会凭空创建错误回调。
// 后续0x868F50把相同key追加到所有者链表；第四批已确认节点只保存int32键。
// 已审登录/房间成功事件及统一错误分派不直接减少此链表；
// 所有者析构会遍历取消回调并释放链表，完整边界见05。

// 服务端统一错误帧
//
// 0x87FD30的wire_type=-1分支顺序读取：scheduler_key DWORD、error DWORD，
// 将剩余地址保存为描述字符串，然后调用0x87E170(key,error)。
// 不要把这两个DWORD误解为玩家ID、房间ID或UI编号。
// 描述字符串的NUL边界必须由完整消息解析保证，本分支没有显式长度参数。

// 错误匹配与清除
//
// 0x87E170查询对应key；未找到则返回，不执行任何bundle回调。
// 找到则调用0x87E2B0(bundle,error)：优先查错误码专用处理器；
// 无专用处理器但bundle+12有默认处理器时，写入错误码再调用其虚表+4。
// 两者都没有时回调阶段无动作，但外层仍继续销毁bundle并移除调度器项。
//
// 外层通过0x82CF20→0x82CF90析构bundle及它拥有的处理器，
// 最后0x8308F0执行树节点重连/平衡、释放节点、减元素数量。
// 因而不能把“UI没有错误提示”推断成“scheduler_key仍在等待”。
// 反之，key未匹配时也不能期待某个任意type回包触发此收尾。

// 重复与乱序
//
// 同key重新登记会销毁旧bundle；旧请求稍后来的错误可能匹配新bundle。
// 本次恢复没有发现额外的请求流水号参与此key查找；
// 这表示服务端不应把重试/重复错误当成天然可幂等的关联响应。
// 第一次错误命中后会erase，再来的同key错误一般查不到旧bundle。
// 尚未跑并发重试或证实具体UI误配；这只是当前键模型的约束。
