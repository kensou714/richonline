// 先分清三种状态
//
// ErrorScheduler映射：key -> ErrorBundle，决定错误帧找到哪个处理器。
// 所有者请求键链表：保存本对象曾登记的key，供对象析构时取消回调。
// UI等待：由管理器+600/+601和具体界面/事件收尾控制，见02、03。
// 三者生命周期不同。链表非空、scheduler仍有key，都不能单独证明UI卡住。

// 链表布局：以构造、节点写入、迭代和释放交叉验证
//
// 容器从0x82D270→0x8314D0构造，总占用12字节：
//   +00  分配器/实现前缀；本批不命名其全部语义。
//   +04  哨兵节点指针。
//   +08  元素计数；构造为0，86B2D0插入时递增，837F40清空时归零。
// 节点由86B190分配12字节，经86B940构造：
//   +00  next 指针。
//   +04  prev 指针。
//   +08  int32 request_key；来自传入地址的DWORD解引用。
// 节点没有时间戳、截止时间、重试计数，也没有请求对象或所有者指针。
// 这是当前具体容器的事实，不能据此断言客户端其它层没有计时机制。

// 插入不是“收到一次ACK”
//
// 请求入口先登记ErrorScheduler，再取scheduler+10的所有者链表。
// 若链表指针非空：868F50(key)→869670(&key)→86AA70(end,key地址)。
// 831610给出end哨兵；86AA70在哨兵前插入新节点并修复前后链接。
// 868F50伪码把key写成char；86B940汇编按DWORD复制，不能据此截断key。
// 插入链没有查重。同一所有者连续发同key请求，会保存多个相同键。

// 具体所有者位置
//
// 登录派生对象：8554D0在this+0xC8构造，855600在同偏移调用82CBA0析构。
// 房间派生对象：84E220在this+0x48构造，84E340在同偏移调用82CBA0析构。
// 这里偏移由汇编add ecx核对；不能使用伪码省略this后显示的无参调用猜测。
// 其它对象也有同类成员，lifecycle_xrefs.json保留构造/析构入口静态交叉引用。
// 尚未逐个恢复那些对象的类名和字段偏移。

// 所有者销毁：82CBA0的完整本地链
//
// begin = 8315A0；end = 831610；831760比较迭代器是否尚未到end。
// 831670→835CD0→837F00取节点+8的key。
// 对每个key调用全局调度器82CE00：找到bundle则销毁并从树中erase。
// 8316C0→835C70→838290推进到next；这里不是删除链表节点。
// 遍历完成后831550→835AD0→837F40：先重置哨兵、计数归零，
// 再逐节点释放；835AD0最后释放哨兵本身并把容器+4清零。
// 因而回调取消和链表内存释放是前后两个阶段，不是循环里边走边删同一容器。

// 成功、错误、替换、析构的区别
//
// 已审登录完成855B10、房间事件886FB0/887310负责业务与UI通知；
// 没有证据表明它们把所有者链表当通用ACK队列逐项移除。
// wire-1→87E170：回调、bundle析构、树erase；不触碰上述所有者链表。
// 868E50：同key重新登记前调用82CE00取消旧bundle，再绑定新bundle。
// 82CBA0：所有者析构时逐key调用82CE00，末尾释放整个链表。
// 当前IDB中82CE00仅经611E03跳板被82CBA0和868E50直接调用。
// 这是静态直接交叉引用结果；未把未恢复的间接调用排除为“不可能存在”。

// 排障含义与需要动态确认的风险
//
// 成功后仍保留key不能直接登记为泄漏或卡等；先核对对象是否仍存活及UI是否收尾。
// 相同key的调度器映射只有一份，重复发送会替换旧bundle，但链表可有多个键副本。
// 已被错误路径erase的key，在所有者析构时再次取消通常只会查不到并返回。
// 若旧所有者A和新所有者B可同时登记同key，A后来析构会按key取消当前映射，
// 没有额外owner/token检查保护B的bundle。代码满足这一条件风险，
// 但是否实际允许两个所有者以该顺序并存，本批未运行游戏验证，不标必现BUG。
// 未来实现服务端/客户端补丁时，不能把“延迟错误按同type回来”视为天然关联正确。
