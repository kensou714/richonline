// 核心结论
// G+0x14777不是靠一个普通服务器回复自动清零的通用“等待响应”字段。
// 本轮确认0x6021处理器将其置1，并启动一个打开UI36、等待至少两秒、
// 请求主状态4的后继流程。不能只看到消费停止就诊断为永久卡死。
// UI36在当前Intf资源映射为G_GameOver.ui；该命名是资源事实，
// 不能进一步推断所有游戏结束结果、奖励结算或网络断开都由此完成。

// 已核对的链
// 0x7EE330注册code 0x6021 -> 0x6031F5跳板 -> 0x7F1610。
// 0x7F1610将cdecl(G, packet)转换为thiscall，packet压栈、G放ECX。
// 经0x610D8C到0x67E410：写BYTE[G+0x14777]=1，
// 写DWORD[G+0x98]=GetTickCount()，不读取packet正文，retn 4。
// 0x7BB290随后因该标志非零而不继续出队；见01篇完整门控说明。

// 两秒后继：0x650460
// 标志非零且UI36尚未处于检查要求的状态时，调用UI管理器的状态设置、
// 打开和数据通知路径；没有把这段误写成“等待服务端UI36回应”。
// 以无符号GetTickCount()-DWORD[G+0x98]比较0x7D0，即2000毫秒。
// 达到阈值则push 4，调用0x601553 -> 0x629DC0。
// 0x629DC0只写全局DWORD[0xA6723C]=4并返回4。
// 本函数不清G+0x14777；其作用是请求主状态转换，而非恢复旧队列。
// 0x624CA0按0xA6723C索引funcs_624D93并执行相应状态处理器。
// 状态表、线程和旧业务对象析构顺序继续由“启动线程与退出”专题恢复。

// 更新与抑制的影响
// 0x64F780在标志为0时才执行部分棋盘更新；其他更新仍然运行。
// 其后照常调用0x610EF4 -> 0x7BB290，但消费者内部会再检查该标志。
// 0x624E80也是消费者调用者；不能仅按0x64F780推断唯一调用频率。
// 0x6501E0在标志为1时跳过一个按键/UI72入口。
// 0x6BAEA0在标志为1时跳过悬浮信息绘制分支；完整信息绘制尚未逐项审阅。
// 0x7BB530在标志为1时跳过按当前事件状态自动选择的分支；其状态语义另查。
// UI窗口输入路径也读同一getter，具体按键门控由“输入与快捷键”专题跟进。

// 构造与覆盖边界
// 0x7BAE60构造路径清BYTE[G+0x14777]及DWORD[G+0x98]。
// 在原.text中搜索14777h的完整disp32，仅匹配getter、setter、构造三函数；
// 这是候选定位方法，不证明没有基址调整、块清零、别名或间接写入。
// 本轮没有观测运行中的字段，也没有证明旧G的确在某时刻被释放。

// 来源与调试意义
// 0x6021由本地小记录构造；大厅0x12分支可以触发它。
// 请求字段、管理器ID匹配、替代分支详见../游戏分派桥接/03_6021来源与状态切换边界.txt。
// 因而抓包未看到网络6021不代表这条事件不存在。
// 若两秒后仍停留，应分别核对650460是否运行、Tick差值、A6723C是否变4、
// 状态4处理器是否实际执行；上述均为建议观测点，非本轮实机观测结果。
